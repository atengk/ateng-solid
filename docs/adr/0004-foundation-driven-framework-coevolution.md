# ADR-0004: “独立通用底座 + 零补丁上层框架”双生演进模型与三层能力边界

- **状态**：`Accepted`
- **日期**：2026-11-20
- **作者**：Ateng
- **影响范围**：`ateng-solid` 全工作区、子工程定位及与 `ateng-boot` / `ateng-cloud` / `ateng-ui` 的协同研发流程

---

## 1. 背景与战略目标

在企业级脚手架和底座的长期研发中，常见两种极端退化形态：
1. **上层打补丁妥协**：业务项目在遇到基础设施库缺口或 Bug 时，图快在上层编写大量拦截器、字段映射器或兼容 Hack；久而久之，上层工程沦为补丁堆砌，而底层底座始终处于“Demo 级好用、生产真用就掉链子”的状态；
2. **底层被上层绑死**：为了方便某个具体业务项目，直接在基础设施库中写死业务表名（如 `sys_*`）、角色标识（如 `super_admin`）、错误码段或特定默认租户，导致底座丧失独立性，无法在其他外部项目中开箱使用。

`ateng-solid` 的真实核心定位是：**以高标准上层工程实战倒逼并锤炼基础设施底座，同时将自身沉淀为一套纯净、零补丁、可直接面向二次开发的开源全栈上层框架**。

---

## 2. 核心决策

1. **确立三层能力边界模型（严防上下越界）**：
   - **第一层（通用独立底座：`ateng-boot` / `ateng-cloud` / `ateng-ui`）**：保持 100% 脱离 `ateng-solid` 独立运行与发布的能力，只接收具备跨项目复用价值的通用抽象，并通过配置开关（`@ConfigurationProperties`）、SPI 钩子或回调 Prop 保持向后兼容默认行为；
   - **第二层（上层框架内核：`ateng-solid`）**：承接企业级系统高频共性的认证会话、可开关多租户、组织架构、RBAC + `@DataScope`、字典参数、审计日志及管理台壳；**绝不滞留本应下沉底座的技术能力，绝不编写掩盖底座不足的临时降级代码**；
   - **第三层（二开业务扩展层：`biz-*`）**：基于 `ateng-solid` 的具体行业业务扩展，按域挂接，不篡改或侵入框架内核（`auth`/`system`）。
2. **硬停工零降级铁律（Zero Workaround）**：
   - 上层规划或编码发现任何底座缺口（含权限路由、上下文同步、缓存隔离、布局组件扩展点等）时，立即暂停受阻特性的编码，先提报通用化 Issue 并在底座仓完成改造、独立测试与**递进正式发版**；
   - 清除 `foundation-enhancements-checklist.md` 中所有鼓励在上层编写绕过代码的“临时降级方案”，确保上层框架每一行正式代码都直连底座规范能力。
3. **双轴验收门禁（解封恢复上层前 4 项硬校验）**：
   - **无项目污染审计**：底座源码与测试零 `ateng-solid` 专属业务名词/约定；
   - **独立可运行**：底座自带单测与 Sample 工程无需 `ateng-solid` 即可单独验证通过并保持默认向后兼容；
   - **正式版本闭环**：底座已完成递进正式发布（Maven Central / npm 正式版，不覆盖既有版本号），上层显式升级锁版后再合入业务代码；
   - **上层纯净复核**：上层仅存在标准配置与薄 SPI 装配，零残留过渡判断。
4. **规划期与编码期节拍分离**：
   - 在底座阻断单未完成发版前，上层仅聚焦架构梳理、详设 Spec（如 DDL 与接口时序）及底座 Issue 提炼，**严禁提前动工编写受阻塞的业务代码**。

---

## 3. 后果与权衡

- **优点**：实现“底座真正生产就绪且独立开源可用”与“上层形成零补丁、极简优雅的企业级开发框架”的双赢闭环；极大提升未来基于 `ateng-solid` 二开与多端拓展的可维护性。
- **代价**：底座缺口期会主动阻塞上层相关模块的编码进度，需要严格自律克制“先在上层糊一下跑起来”的冲动，先把底座打磨发版再稳步推进上层。
