# ADR-0004: “独立通用底座 + 零补丁上层框架”双生演进模型与双阶门禁

- **状态**：`Accepted`（`2026-11-26` 修订：废除“未发版禁编码/禁提交 `dev`”，确立“`dev` 本地协同放行 + `main`/发版锁版硬门禁”）
- **日期**：2026-11-20（修订：`2026-11-26`）
- **作者**：Ateng
- **影响范围**：`ateng-solid` 全工作区、子工程定位及与 `ateng-boot` / `ateng-cloud` / `ateng-ui` 的协同研发流程

---

## 1. 背景与战略目标

在企业级脚手架和底座的长期研发中，常见两种极端退化形态：
1. **上层打补丁妥协**：业务项目在遇到基础设施库缺口或 Bug 时，图快在上层编写大量拦截器、字段映射器或兼容 Hack；久而久之，上层工程沦为补丁堆砌，而底层底座始终处于“Demo 级好用、生产真用就掉链子”的状态；
2. **底层被上层绑死**：为了方便某个具体业务项目，直接在基础设施库中写死业务表名（如 `sys_*`）、角色标识（如 `super_admin`）、错误码段或特定默认租户，导致底座丧失独立性，无法在其他外部项目中开箱使用。

`ateng-solid` 的真实核心定位是：**以高标准上层工程实战倒逼并锤炼基础设施底座，同时将自身沉淀为一套纯净、零补丁、可直接面向二次开发的开源全栈上层框架**。

> **2026-11-26 演进修订说明**：早期版本同时要求“底座未发正式版前禁止编码且禁止向 `dev` 提交 `-SNAPSHOT`/`yalc`”。在多包底座高频协同实战中，每次微小修复都强行切正式版受制于外部仓库发版频次与周期，反而造成上层本地改动和 Issue 大量积压。故保留“零补丁下沉”与“底座独立性”红线不变，将“正式版锁版门禁”从 `dev` 研发期后移至 **`main` 合入与 Release 发版阶段**。

---

## 2. 核心决策

1. **确立三层能力边界模型（严防上下越界）**：
   - **第一层（通用独立底座：`ateng-boot` / `ateng-cloud` / `ateng-ui`）**：保持 100% 脱离 `ateng-solid` 独立运行与发布的能力，只接收具备跨项目复用价值的通用抽象，并通过配置开关（`@ConfigurationProperties`）、SPI 钩子或回调 Prop 保持向后兼容默认行为；
   - **第二层（上层框架内核：`ateng-solid`）**：承接企业级系统高频共性的认证会话、可开关多租户、组织架构、RBAC + `@DataScope`、字典参数、审计日志及管理台壳；**绝不滞留本应下沉底座的技术能力，绝不编写掩盖底座不足的临时降级代码**；
   - **第三层（二开业务扩展层：`biz-*`）**：基于 `ateng-solid` 的具体行业业务扩展，按域挂接，不篡改或侵入框架内核（`auth`/`system`）。
2. **零补丁本地协同原则（Zero Workaround, Co-Evolution First）**：
   - 上层规划或编码发现底座缺口或缺陷时，**严禁在上层编写临时降级/绕过补丁**，应直接提报通用 Issue 并在对应底座仓完成本地通用改造与独立单测；
   - 底座通过 `-SNAPSHOT`（`mvn install`）或 `pnpm pack + yalc` 刷新本地联调产物后，上层**即可在 `dev` 分支直接继续编码、自测并提交代码（包括含 `-SNAPSHOT` / `file:.yalc` 的清单文件）**，不再冻结开发进度。
3. **双阶门禁分离（`dev` 放行协同 vs `main` 强锁正式版）**：
   - **`dev` 日常开发态**：不限制 `-SNAPSHOT` 与 `yalc` 依赖提交，以本地全量离线验证通过为准（联调期内因远端无本地未发版构件导致的 `dev` CI 失败属于已知可接受状态）；
   - **`main` 主干与发版强守门**：在合并 `dev -> main`、推送 `main`/`v*` 标签及执行 Release 流水线前，必须完成 **4 项双轴验收门禁**：
     1. **无项目污染审计**：底座源码与测试零 `ateng-solid` 专属业务名词/约定；
     2. **独立可运行**：底座自带单测与 Sample 工程无需 `ateng-solid` 即可单独验证通过并保持默认向后兼容；
     3. **正式版本闭环**：底座已完成递进正式发布（Maven Central / npm 正式版，不覆盖既有版本号），上层已还原锁定正式版；
     4. **上层纯净复核**：上层仅存在标准配置与薄 SPI 装配，零残留过渡判断。
   - 上述锁版校验由两子仓 `.githooks/pre-commit`（拦截直提 `main`）、`.githooks/pre-push`（拦截推送 `main` 与 `v*` 标签）、GitHub Actions `ci.yml`（`main`）与 `release.yml` 强制阻断守护。
4. **特性闭环与发版锁版解耦**：
   - 上层 `[server]` / `[admin-web]` 业务或缺陷 Issue，只要**关联底座改造已在底座 `dev` 分支落盘提交并通过单测**，且**本仓在 `dev` 提交并通过本地全量离线测试**，即可立即关单；
   - 未发正式版的锁版收口统一在 [`foundation-enhancements-checklist.md`](../specs/foundation-enhancements-checklist.md) 与发版检查工单中集中跟踪，于 `dev -> main` 前统一解锁。

---

## 3. 后果与权衡

- **优点**：兼顾“底座独立通用、上层零补丁纯净”和“多包底座与上层高频本地联调不堵车”，彻底消除本地工作区与日常 Issue 积压；同时通过 `main` / `pre-push` / Release 多重门禁守住正式交付可复现底线。
- **代价与约束**：`dev` 分支在本地联调窗口期内允许存在未脱离本机的 `-SNAPSHOT` / `yalc` 引用，期间远端 `dev` CI 可能红灯且他人跨机检出 `dev` 需先对齐本地底座产物；所有正式对外交付与生产构建必须经 `main` 与 Release 锁版门禁收口。
